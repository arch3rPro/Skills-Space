## 1. 产品定位与用户任务

**创意工坊管理技能的创作过程和源文件；原 Agent 完成创作，Skills Space 帮用户看产物、检查效果、评估和安装。**

用户已明确：使用用户自己的 Agent；以 `skills use` 为基础；生成通用技能；评估能力可复用于其他技能；源文件留在创意工坊目录；安装复用托管技能流程。GUI 以展示与必要能力补充为主。

第一版建议形成完整闭环：

```text
填写用途与要求 → Agent 返回方案 → 对话修改或确认 → Agent 构建技能
                                  ↓
                           在工作台继续对话修改
                                  ↓
                  可选试用 → 可选评估 → 安装技能
```

试用、评估不是安装的强制前置步骤；用户可在已有可用产物时直接安装。页面不做强制步骤条，不要求先把所有项目打满分。

| 用户要完成的事 | 用户动作 | 可观察结果 |
| --- | --- | --- |
| 从一个想法创建技能 | 写用途与要求，选 Agent，开始创作 | 工作台保留原 Agent 的回复和活动；文件区显示实际方案与产物 |
| 改进已有草稿 | 在工作台继续对话，必要时刷新磁盘文件 | 预览／源码与磁盘一致；旧评估按内容版本保留 |
| 看技能是否有用 | 用一个真实任务试用 | 原 Agent 给出实际输出；可将输入／输出用于后续评估 |
| 获取质量意见 | 选择评估范围并运行评估 | 得到带证据的评估报告；源技能未被评估过程改写 |
| 安装到 Agent | 从当前产物进入现有安装向导 | 原版 add 执行并显示原有逐项结果；源目录保留 |
| 评估已有托管／原生技能 | 从技能详情更多菜单进入评估 | 使用同一评估能力；不要求先复制成一条工坊创作 |

## 2. 测试结论如何改变方案

| 已有证据 | 方案取舍 | 尚不能据此声称的能力 |
| --- | --- | --- |
| Codex、Pi 均完成创建、同会话修改、两例试用和只读评估 | 首批创作 Agent 采用 Codex、Pi；当前已按用户确认的对话工作台接入原结构化进程，产品接入验证与既有模型内容实测分开记录 | 本次正式GUI全部任务已验收、其他 Agent 同样通过 |
| 同一份 Codex 产物由 Pi 直接运行成功 | 技能内容遵循 Agent Skills，创作 Agent 仅作为记录，不成为技能适用范围 | 任意技能、任意工具依赖均可跨 Agent 运行 |
| 原版 use 可打印完整指令和资源位置 | 统一以原版输出准备任务，桌面层只负责交给原 Agent | 上游已经支持 `--agent pi` |
| 两次评估均未改技能文件 | 评估与修改分成两个动作；评估结果不自动回写 | 一份自然语言指令具有 OS 沙箱的强制隔离能力 |
| 两组报告格式不同，试点评分均为 100，仍保留建议／未测范围 | 需要独立、结构化、带证据的评估技能；页面不能用一个大分数代替结论 | 100 分代表泛化质量或已经验证自然触发 |
| 现有本地来源预览正确识别两组产物 | 工坊安装预填本地来源，完整复用安装向导 | 真实安装、后续复制／链接更新已在本次实验验证 |

本轮新增设计必须单独验证：短启动请求读取任务文件、终端的跨平台启动、评估统一格式、应用重启后的草稿恢复、安装后的源文件关系。复用已通过的 creator 内容加载与案例证据，不重复跑相同实验。

## 3. 第一版范围

### 3.1 首次可交付版本

- 创意工坊列表；新建创作、打开目录、修改需求和删除创作。
- 单条创作对应一个主要技能；查看技能预览／源码和已发现的关联资源。
- 使用已安装的 Codex、Pi 原版结构化执行接口，在工作台继续对话；沿用原 Agent 的登录与模型配置。
- 用当前草稿执行用户给出的试用任务；支持保留输出作为评估材料。
- 独立只读评估技能、评估报告与适用范围；内容变化后不把旧报告当作当前结果。
- 由工坊安装当前产物到托管技能；复用现有本地来源、目标选择、确认、结果和冲突处理。
- 托管／原生技能详情更多菜单增加“评估技能”，复用同一个评估页面和执行能力。
- 本地持久保存；重启可回到创作和报告，正常导航保留列表条件。

### 3.2 后续候选

- 从现有技能创建一个可编辑副本；须明确保留原技能、复制到工坊，不能直接把原生目录当工作目录。
- 将具体评估建议交给创作 Agent；用户明确选择建议后再修改，不自动采纳全部建议。
- 更多创作 Agent、完整试用输出采集、同任务版本对比、导出分享。

首版不加入独立模型服务、模型／Provider／账号配置、内置代码编辑器、自动优化循环、Git 分支管理、批量评分、夜间训练、发布市场或自动同步。上述内容不是必须经过的技术前提。

## 4. 页面与交互

### 4.1 导航与工坊列表

侧栏主入口建议为“技能商店／技能空间／创意工坊”，全局与项目 Agent 导航保持原位。工坊是源文件工作区，不增加全局／项目筛选；安装时再明确安装范围。

```text
创意工坊

[搜索创作…                         ]      [↻ 刷新] [＋ 新建技能]

┌──────────────────────────┐  ┌──────────────────────────┐
│ 会议纪要整理          ⋯  │  │ 接口检查清单          ⋯  │
│ 整理讨论内容、行动项和   │  │ 根据接口约定检查常见问题 │
│ 尚未确定的事项           │  │                          │
│ 昨日更新    [查看评估]   │  │ 尚未生成技能             │
└──────────────────────────┘  └──────────────────────────┘
```

此图只表达信息位置，样式使用现有 InventoryCard、InventoryCardHeader/Footer 和 InventoryToolbar，不新增工坊专属卡片皮肤。卡片整面进入创作详情；内部按钮不触发整卡导航。没有启停开关，没有安装目标 Agent 图标，没有安装到几个 Agent 的统计。

| 字段／动作 | 建议规则 |
| --- | --- |
| 搜索 | 搜索创作名称、需求和当前技能名；默认空；沿用现有输入高度和导航内保留策略 |
| 排序 | 默认按源内容最近更新时间降序；首版不增加排序控件 |
| 名称 | 使用用户给创作起的名称；与生成技能内部标识分开，不把用户中文名称强制改为 slug |
| 简介 | 已有技能使用其 description；未生成时使用需求开头；两行截断，复用 OverflowText |
| 更新信息 | 根据工作区源内容变化记录；不能把打开页面的时间当成更新 |
| 评估入口 | 有当前或历史报告时提供“查看评估”；卡片不堆总分、分项分数和验证警告 |
| 未生成 | 简短“尚未生成技能”，详情仍可打开，能继续创作和修改需求 |
| 更多菜单 | 修改需求、打开目录、删除创作；不用菜单重复主要操作 |
| 刷新 | 重读工坊源文件与报告；不启动 Agent、不调用模型 |
| 空状态 | 复用现有 Empty；文案“创建你的第一个技能”，主操作“新建技能” |

初期不增加“全部 Agent／来源／配置／预设”等无助于找草稿的筛选器。创作时用过的 Agent 不定义技能可运行的平台。

### 4.2 新建技能

复用现有 Modal、FieldGroup、Field、Input、Textarea 和单选 Agent 组合。单页即可填写，不另做多步向导。

```text
新建技能                                             ×

名称
[会议纪要整理                                      ]

用途与要求
[把会议速记整理成纪要，保留负责人和原始日期，        ]
[没有确定的事项不要写成结论。                        ]

创作 Agent
[Pi                                               ▾]

                                    [取消] [生成方案]
```

| 字段 | 必填、默认与限制 | 行为与保存 |
| --- | --- | --- |
| 名称 | 必填；建议 1–80 个字符；去除两端空白；支持中文，不接受纯空白 | 用于创作展示，不拼接为执行目录；重复展示名允许，内部 ID 唯一 |
| 用途与要求 | 必填；多行；建议上限 8,000 字符，附件式长材料通过打开目录加入 | 写入需求文件；保存为用户输入内容，不替用户扩写未经确认的要求 |
| 创作 Agent | 必选；仅列产品已接入且检测到可执行文件的 Codex／Pi；默认上次成功使用者，否则第一个可用项 | 只选执行 Agent，不在这里配置模型、Profile、预设、工具权限或账号 |
| 开始创作 | 有可用 Agent 时为主操作；输入有效且已选择 Agent 才可用 | 先保存工作区，再准备原版 creator；成功启动终端后结束弹窗 |
| 无可用 Agent | Agent 字段无默认选中值；提供现有设置入口；主操作改为“保存草稿” | 名称与用途有效即可保存，回到草稿详情；不会启动进程或丢失输入 |
| 启动失败 | 草稿已保存，不删除已有内容；沿用错误通知 | 返回该草稿可再次启动，不能报“技能创建成功” |

名称长度和需求上限是本方案建议的产品值，确认后实施。暂不加独立附件处理系统；参考文件可经“打开目录”加入 input/，Agent 按需求读取。文件类型能否处理取决于原 Agent 的实际能力。

### 4.3 对话工作台（当前方案）

核心流程为：新建并填写要求 → Agent 返回构建方案 → 用户在同一对话中修改或确认 → Agent 构建技能。后续范围内修改继续直接对话；范围变化才再次确认。独立原型仍为内存模拟；正式接入使用同一工作台组件和原 Agent 结构化进程，不共用模拟数据。

```text
‹ 创意工坊                  会议纪要整理                 [安装技能] [⋯]

┌ 与 Pi 的连续对话 ─────────────────┐ ┌ 文件工作区 ───────────────────────┐
│ 你：我想创建会议纪要技能…         │ │ PLAN.md        │ PLAN.md          │
│                                  │ │ skill/         │ 构建方案正文     │
│ Pi：已整理构建方案。 [PLAN.md]    │ │   meeting…/    │                  │
│                                  │ │     SKILL.md   │ 工作方式         │
│ 你：先列行动项，再列待确认。     │ │     references/│ 输出结构与示例   │
│ Pi：方案已更新。 [PLAN.md]       │ │       output…  │ 文件安排         │
│                                  │ │                │ 执行范围         │
│ 你：按方案开始构建。             │ │                │                  │
│ Pi：构建完成。 [SKILL.md] [模板] │ │                │ 点击目录查看文件 │
├──────────────────────────────────┤ │                │                  │
│ [继续对话…                     ] │ │                │                  │
│                             [↑]  │ │                │                  │
└──────────────────────────────────┘ └────────────────┴──────────────────┘
```

- 左侧保留完整的用户与 Agent 消息。方案反馈和确认都作为对话回合，不再用修改需求／调整方案弹窗串接任务；确认快捷操作也发送一条明确的用户消息。
- 右侧是文件目录树与所选文件正文，不使用技能详情的预览／源码标签或文件下拉。方案作为 `PLAN.md`；只有构建完成后才出现 `skill/<name>/SKILL.md` 与资源文件；报告作为 `review/review.md`。文件只读展示，修改要求从对话提出。
- 方案返回和对话调整后，自动打开当前 `PLAN.md`；确认后的执行持有方案快照，完成后打开技能文件。点击消息中的文件引用与点击目录树访问同一文件。
- 文件夹可展开／收起，文件可键盘聚焦与选择。文件正文与目录始终作为统一文件区整体展开／收起，不再自动隐藏其中一部分。会话与正文分别滚动，标题与输入区不随消息增长移动。
- 构建过程中只显示具体活动、停止和耗时；保留旧产物。未确认不生成技能，停止保留对话与已有文件；另一个草稿不能替换运行中的任务。
- 新建只有名称、用途与要求、Agent 和“开始对话”。安装继续复用现有安装流程，评估和试用留在更多操作，不进入创作主流程。
- 现有 shadcn CLI 未提供 `message`／`message-scroller` 文档或组件入口，本轮不引入未经确认的新组件依赖；用当前消息行、Card、Textarea 与 SidebarMenu／Collapsible 组合实现原型。正式组件选型与 Agent 执行仍待接入设计。

### 4.4 试用

详情更多菜单提供“试用技能”；复用短任务 Modal：选择已接入 Agent、填写一个真实任务。已有草稿和任意已安装技能均可复用底层能力，但首版只开放工坊入口，其他页面按确有需求扩展。

试用给原 Agent 显式加载当前内容并执行这个任务。用户可在原终端继续交互；不把一次成功试用表述为自然触发有效。首版保持手动刷新和轻量结果保存，不从终端滚动文本猜测答案。

评估需要实际输出时：支持从用户已保存的文本文件导入或粘贴输出，并保留输入、输出及来源为“用户提供”；可靠的原 Agent 结构化执行结果可直接保存并标明执行 Agent。两种证据不能混称。没有输出时可做结构评估，不自动花费模型额度补跑案例。

### 4.5 评估页面

工坊详情在原文档的预览／源码同行提供“评估”Tab；已有报告在该Tab展示，详情下方不重复追加报告。完整评估执行与历史内容关联属于 C 批次，首批只读已有 report.md。任意技能详情更多菜单的“评估技能”进入同一评估视图，返回时保持原全局／项目、Agent 和列表条件。外部技能不自动变成工坊草稿。

```text
评估

[开始评估]     上次评估 · Pi · 11月4日

结构评估  52 / 60       实际任务  未评估

结论与主要问题
… 具体问题、影响及文件／输出证据 …

… 评估正文 …

▸ 本次任务与输出
▸ 历史评估
```

| 项目 | 规则 |
| --- | --- |
| 默认范围 | 无真实输出时为结构评估；已有明确关联的任务输出时，可选结构加实际任务 |
| 评估 Agent | 默认上次可用者，可选择首批支持的 Codex／Pi；新会话运行，不继承创作对话 |
| 结构分 | 首版沿用试点的四项 60 分：元数据 10、任务流程 20、可移植性 15、资源与简洁性 15；分数附具体证据，不按警告或规则数量加分 |
| 实际任务分 | 有任务和真实输出时评估；首版约定 40 分，明确每个检查的权重和判定证据；具体任务标准来自用户认可的目标 |
| 无证据 | 显示“未评估”，不计为零，不模拟补分，不把结构分换算成 100 |
| 总分 | 仅在本次约定的全部评分证据齐全时显示；不在工坊列表做质量排行榜 |
| 主要结论 | 优先展示会影响任务结果的实际问题、证据和改进建议；完整分项放在报告中 |
| 非量化技能 | 可仅给结构意见与人工定性结论；不强制为主观风格任务虚构客观成功率 |
| 内容已变化 | 历史报告保留，标注“基于之前的内容”；不套用到当前稿，不在每张卡片加常驻警告 |
| 评估失败 | 保留历史报告及可阅读的新文本，不能用上次成功覆盖本次失败；不自动重试 |

建议新增项目自有的通用只读评估 Skill，以 darwin 的结构／效果区分和 Anthropic grader 的逐项证据方法为参考，保留出处及实际借用内容对应的许可。不把原版 darwin 的 Git、自动修改、作者生态偏好及多轮评审整体搬入产品；SkillOpt 暂不作为首版依赖。

该评估 Skill 与工坊 UI 解耦，按固定版本随应用提供，生成 Markdown 报告及稳定 JSON 评分结果。最小 JSON 包括 schemaVersion、结构分项、实际检查结果、问题与证据；源内容版本、执行 Agent、时间、记录 ID 由应用记录，不信任模型自行宣称。

模型返回的数据要检查结构、分值范围和证据是否存在。格式不合法时仍可查看原报告，评分区域说明“评分结果未能读取”；不伪造分数或自动跑一遍评估。当前实验两组报告格式不同，统一格式是有依据的新增工作。

## 5. 源文件、记录和安装关系

### 5.1 工作区与持久化

建议默认根目录为应用数据目录的 workshop/；使用系统路径 API，提供打开目录操作，不硬编码任何开发者路径。首版不加目录迁移向导或存储设置页。

```text
workshop/
  drafts/<id>/
    draft.json                  # 展示名称、Agent 选择、主要技能相对路径
    CREATION.md                 # 用户要求
    input/                      # 用户主动加入的参考材料
    skill/<skill-name>/          # 真正可安装的技能根目录
      SKILL.md
      references/…
  reviews/<run-id>/
    input/                      # 本次技能内容副本
    cases/                      # 本次使用的任务与真实输出
    report.md
    report.json
    run.json                    # 输入内容版本、Agent、时间和运行结果
```

- 一条创作使用稳定 ID；用户修改展示名称不会移动目录。真实技能目录名与 frontmatter name 对齐。
- 元数据只保存导航和任务关联，技能内容仍以磁盘文件为准；不能用缓存覆盖外部编辑。
- 评估针对某一份输入内容；在独立目录放内容副本和报告，避免评估直接在正式技能目录写文件。前后对比副本和原源文件的清单／哈希，异常时该报告不能标为只读完成。
- 输入副本不是 OS 沙箱。生产环境使用原 Agent 的权限和登录，不沿用实验中的凭证复制方法，不宣称目录隔离阻止了全部越权访问。
- 原始会话、认证信息和令牌不写入工坊记录。源技能写入由用户 Agent 完成；工坊只写需求、记录、受用户授权的文件副本与报告。
- 不做默认全量版本库。评估记录保存对应输入版本即可；源文件删除采用现有废纸篓能力，并展示实际要移除的草稿范围。
- 重启后恢复草稿、主要产物和报告；上次进程身份无法可靠核实则不冒称仍运行或已经完成，也不按猜测 PID 结束进程。

### 5.2 安装与后续修改

安装按钮预填已选主要技能的**真实目录**，进入现有本地目录检查和安装向导，沿用原版 add 的目标、作用域、复制／链接、冲突确认及结果。不能另建一个简化安装弹窗。

| 场景 | 行为 |
| --- | --- |
| 安装前技能正在变化 | 复用现有来源内容复核；发生变化时刷新预览，不用旧确认继续写入 |
| 文件复制安装 | 后续工坊修改不自动改已安装副本；用户再次进入现有安装／同步确认更新 |
| 符号链接安装 | 依原版 CLI 的真实链接关系生效；不得承诺内容会保持不变或自动回滚；确认页沿用既有安装方式及影响说明 |
| 删除创作 | 普通草稿进废纸篓，不连带调用 Agent 卸载；如果实际安装关系依赖该源目录，则在删除确认中说明具体影响，不暗中留下失效链接 |
| 已安装目录后来有独立改动 | 沿用既有内容冲突判断；缺少记录不伪装为可安全覆盖 |
| 安装失败或部分成功 | 显示现有逐项结果和可执行的后续动作；草稿保留 |

不另维护“已分发到哪些 Agent”的工坊数据库；安装结果和关系以现有原版记录、实际文件和现有本地同步能力为依据。是否存在真实源目录依赖必须检查当前关系，不能把所有上游符号链接安装都当作直接链接工坊源目录。

## 6. Agent 启动与平台边界

### 6.1 当前接入与历史建议

已确认的工作台方案采用原版 `skills use` 准备 creator，Codex exec JSON 或 Pi RPC 执行、继续原会话；方案回合限制为只读工具，完整方案由 App 保存为 PLAN.md；构建必须核对用户看到的方案快照。下面保留先前终端方案的交接研究记录，不能用来替换当前工作台交互。

先前建议采用两种 Agent 共用的准备链路：原版 `skills use` 输出 → 保存原始指令文件 → 短启动请求让原 Agent 读取指令文件与本轮需求。完整原始输出保留，资源引用可解析；任务要求作为用户请求，不能改写上游 CLI。

这么安排可以使 Codex 和 Pi 使用同样的任务准备流程，并避免把完整 creator 正文塞进平台启动命令。**文件式短启动请求是本次建议，现有实验尚未覆盖，实施时只为这个差异补一次定向验证。**

- 创作与继续：普通交互式原 Agent，用户可在终端自由补充要求。
- 评估和需要可靠输出记录的试用：优先用已验证的 Pi RPC，或者经确认的原 Agent结构化模式；新接入的模式只做必要定向核验。暂不可靠的自动采集路径保留原终端和用户导入结果，不以解析终端文案代替结果。
- Agent 可用性由产品实际能力表与可执行文件共同决定；“系统安装了某个 Agent”不等于已接入创作。上游固定 use 名单不能充当整个工坊的能力名单。
- 只按已安装原 Agent 的现有登录启动，认证和信任由原 Agent 处理。用户自己的模型和 Provider 保留在原 Agent 配置中。
- 任务目录固定为该创作；引用路径必须正确，不能把 source supporting-files 目录当作输出目录。

### 6.2 平台计划

| 平台 | 当前证据 | 实施要求 |
| --- | --- | --- |
| macOS | 现有系统 Terminal 启动实现；Codex TTY、Pi RPC／JSON 实测 | 复用现有启动、观察和清理代码，补新工作区与短请求链路 |
| Windows | 原版 CLI／Agent 的能力不能由旧 Unix 限制推断；现有应用 use 包装尚未接入 | 单独做系统终端启动、路径空格／非 ASCII、进程关闭和参数传递；长技能正文放文件，不作为长命令参数 |
| Linux | 现有应用终端启动未完成，不等于 CLI 不能使用 | 选择实际可用的系统终端；验证工作目录和进程交互，不为每种终端做自定义页面 |

开发顺序先完成一个平台的完整纵向流程，再在同一发布单元补齐另外两平台的启动与关闭。未有真实平台证据时，保留可操作的“复制启动命令”路径并如实标注能力；不在支持平台的首版验收中用跨平台推断代替实测。

## 8. 开发批次与交付条件

以下为已批准设计的实施顺序。有效开发日只用于估算复杂度；以实际缺陷和平台环境修订，不能承诺精确工时。

| 批次 | 范围与交付物 | 复用／新增 | 完成条件 | 估算 |
| --- | --- | --- | --- | --- |
| A 页面与草稿 | 列表、新建／详情、需求文件、实际源内容读取、磁盘持久化；删除及源依赖保护仍待开发 | 复用卡片、工具栏、详情、表单；新增草稿记录 | 创建草稿、外部改文件、刷新、重启可还原；无 Agent 仍可保留草稿 | 1–2 日 |
| B 原 Agent 创作 | Codex exec JSON／Pi RPC 工作台对话、继续、错误处理、资源生命周期 | 复用 use；新增统一任务交接和 Pi 启动适配 | Agent 读到本轮要求并在正确目录产出；退出和失败不丢源文件 | 1–2 日 |
| C 试用与评估 | 试用任务、真实输出导入、通用评估 Skill、结构化报告、内容版本关系 | 复用文档及任务会话；新增独立评估协议 | 有证据才评分，格式错误可查看报告；源文件不改；原生／托管入口复用 | 1–2 日 |
| D 安装与平台收尾 | 工坊安装、冲突／删除影响、Windows/Linux 启动、完整任务观察 | 复用现有本地安装及结果 | 一个完整 GUI 闭环、当前源内容一致、用户能理解复制／链接影响；平台证据单列 | 1–2 日，取决于可用平台 |

单人有效工作量初估 4–8 日，不包括等待平台环境、用户确认或额外范围。A—D 是可审查的代码变更单元，不能每完成一点就反复打包。建议先交付纵向可用的 A+B 演示，再集中完成 C+D 后作为首次完整版本验收；中间演示不标为整个模块已完成。

## 9. 定向验证与停止条件

本轮仅写方案：检查引用、状态和指令一致性，不运行模型、构建或应用自动化。实施时先固定对应批次最小检查清单，复用本次实测，不重复以数量证明质量。

| 风险／用户任务 | 必要验证 | 复用与停止边界 |
| --- | --- | --- |
| 页面职责和可理解性 | 按新建→原终端→看产物→评估→安装审查控件与默认值 | 先做组件／文案审查，再一轮实际流程；不以组件合规替代可用性 |
| 新草稿读写与持久化 | 定向覆盖源文件读取、外部改动、名称／目录边界和一次重启 | 不重跑所有 Agent 配置或技能生命周期 |
| 新文件式启动请求 | 原 Agent 正确读取任务文件、资源和输出目录；每个新适配器一次必要验证 | 既有 creator 加载和案例内容不重测多轮 |
| 源与评估分离 | 文件清单和内容前后核对；旧报告在源变化后成为历史报告 | 使用本地模拟报告核对格式、缺失证据和状态；这些检查不消费模型 |
| 原安装流程交接 | 一个隔离目录完成预览／安装并核对源和目标关系、一次冲突 | 复用原版 add 的已有覆盖；不再实现或测试一套工坊安装引擎 |
| 平台进程适配 | 各平台定向检查启动、工作目录、参数和结束 | 模型内容不按三个 OS 重跑；模拟 Agent 可核对进程合同，真实平台才支持平台通过结论 |
| 实际完整任务 | 一个代表性 Agent 完成 GUI 纵向流程；另一个仅补其特有启动差异 | 不重复完整多 Agent×多平台×多主题矩阵；有具体缺陷才补相关检查 |
| 窄窗口与长内容 | 默认与一个窄窗口观察列表／详情／弹窗必要状态 | 复用全局样式，不自动拓展全部主题／字体；异常文案在对应状态核对 |

构建按项目要求由一个所有者执行，一次 Tauri 构建已包含前端构建时不另跑重复构建。按实际代码风险选择独立行为或 UI 评审，不默认双 Agent 全流程检查。只有新增合同、观测缺陷或失效证据才扩大验证；工具失败沿用已有一次恢复／两分钟停止规则。

## 10. 本次建议确认点

1. 第一版以列表＋双栏创作工作台为主体；当前演示包含输入与协作记录，正式版的原 Agent 消息与执行接口适配仍待开发，不加入模型／账号配置和代码编辑器。

4. 源文件默认保存在应用数据目录；工坊源与安装副本／链接关系遵循现有流程；删除必须尊重真实源依赖。
5. 按 A—D 分批交付，先做完整纵向路径，保留平台验证边界；不按每个参数逐项开放页面。

当前原型以左侧连续对话和右侧文件工作区为主体。方案修改与确认都保留为对话消息；PLAN.md 和构建后的技能／资源通过目录树浏览，无预览／源码标签。之前的执行标签、方案弹窗和双栏详情为已替换的历史设计，验证记录保留在原型说明中。

## 12. 对话修改与范围确认（前一版规则，交互以第 4.3 节为准）

- 初次创建：Agent 给出技能行为、具体输出结构与示例、文件及用途，用户确认后生成。方案不是一段泛化的“先读取再整理”。
- 已有技能：措辞、现有规则、模板内容等已授权范围内的调整，用户发送即执行，不重新走完整方案。完成后显示具体产物与新版本。
- 范围变化：改变技能目标或输出契约、增加文件／依赖、执行脚本、访问服务或当前目录之外的内容，应说明相对已确认范围的变化、影响和文件清单，再等待确认。用户可以调整或“先不改”；取消不动已有文件。
- 正式接入时依据 Agent 提出的结构化动作和实际操作范围判断，不把 App 关键词匹配当作权限判断。当前纯前端原型使用两个明确的模拟回复：补充去重规则直接修改；从 Markdown 改成 JSON 先确认。快捷示例只是原型可体验路径，不表示自由输入已具备真实语义判断。
- 本轮只改前端原型；不调用 Agent、不写真实目录、不提交。验证限定为具体方案展示、一次范围内直接修改、一次输出契约变化确认，并执行一次最终前端构建；不重跑真实执行、安装或主题矩阵。


## 13. 本轮验收边界：对话与文件工作区

验收路径仅为新建→方案文件→一轮对话反馈→方案更新→确认构建→文件树出现技能和资源→点击文件。静态核对单任务／草稿隔离、停止保留文件、已有安装与评估入口。一次最终前端构建；不重复模型、安装、打包、跨主题或平台验证。用户要求不接真实 Agent、不提交。

## 14. 三段式布局调研与实施（历史，收起方式以第18节为准）

用户进一步明确：构建／修改使用工作台，技能查看复用原有详情页；工作台按对话、文件正文、最右目录树组织，文件区应可收起，关闭后对话恢复工作台全宽。上一轮按用户要求先调研；本轮用户已确认实施，代码与验证记录见原型说明。

### 参考与证据边界

- 用户提供的 Codex App 截图直接显示左侧对话、中间文件正文、最右目录树，作为本轮视觉参考。截图不能单独证明拖动／关闭后的状态。
- [OpenAI：Work with files](https://learn.chatgpt.com/docs/artifacts-viewer)：文件可与对话并排查看，自动打开取决于预览设置；公开页面未明确三栏的像素宽度和全部折叠交互，不据此声称 Codex 的精确尺寸或行为。
- [Zed：Parallel Agents](https://zed.dev/docs/ai/parallel-agents)：Agentic 布局将 Agent／会话放左侧，项目等面板放右侧；支持调整侧栏宽度。[面板尺寸参考](https://zed.dev/docs/reference/all-settings#agent-panel)说明按比例布局与固定宽度是独立选择。
- [Cursor：Agents Window](https://cursor.com/docs/agent/agents-window)：Agent 窗口内可以检索和查看文件，与传统编辑器并存。[Plan Mode](https://cursor.com/docs/agent/plan-mode)明确支持通过对话或 Markdown 文件调整方案，再开始构建；常规小修改可以直接使用 Agent。

### 建议布局与操作

```text
构建／修改                                      [文件] [查看技能]
┌──────────────────┬──────────────────────┬───────────────┐
│ 连续对话         │ 当前文件正文         │ 文件目录      │
│                  │ PLAN.md / SKILL.md   │ PLAN.md       │
│                  │                      │ skill/...     │
│                  │                      │   SKILL.md    │
│                  │                      │   references/ │
│ [发送消息…     ] │                      │               │
└──────────────────┴──────────────────────┴───────────────┘
```

- 三段独立，目录树位于正文右侧；不再嵌套到窄的文件 Card 内。工作台使用主内容区的可用宽度，详情页继续使用原阅读宽度。
- 目录树建议初始 176px，作为本项目的设计值而非上游尺寸；支持拖动和独立收起。对话／正文分隔也可调整，窄窗口优先收起目录，避免三列硬挤。
- 主“文件”入口控制整个文件区：同时关闭正文和目录，真正释放宽度给对话。仅收起目录时正文仍保留，避免两个操作含义混淆。
