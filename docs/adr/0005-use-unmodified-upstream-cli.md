# ADR 0005: Use the unmodified upstream CLI

- Status: Accepted; application runtime implemented on codex/upstream-native-refactor
- Date: 2026-10-12
- Reviewed: 2026-10-13
- Supersedes: [ADR 0001](../archive/legacy-managed-phase.md) (dedicated fork), [ADR 0003](../archive/legacy-managed-phase.md) (managed registry protocol), and the managed-protocol wording of [ADR 0004](0004-upstream-lockfile-authority.md). [ADR 0002](0002-local-configuration-and-secrets.md) retains only the principles described in its current-applicability section.

Skills Space will use the original upstream `skills` CLI for core skill lifecycle operations and stop maintaining a separate CLI or fork. This keeps core behavior aligned with upstream and removes the cost of maintaining a second execution engine; the desktop application owns graphical interaction and extensions that upstream does not provide.

Explicit extension accepted 2026-10-17: DeepSeek Harness is an application Agent identity mapped to the original CLI `universal` target at process invocation. The generated upstream registry and CLI bytes remain unchanged. The initial read-only boundary is extended by the explicitly approved [spec 0009](../specs/0009-dsh-native-skill-management.md): version-qualified, static user-profile skill settings, invocation metadata on independent DSH files, and reviewed OS Trash removal. Complex/dynamic configuration and shared/CLI/package resources remain read-only through these native operations. Rust owns locked, revision-checked atomic writes; helpers only prepare YAML. See [spec 0007](../specs/0007-deepseek-harness-skill-management.md) for the original mapping and classification.

Explicit extension accepted 2026-10-17: [Hermes skill settings](../specs/0008-hermes-skill-management.md) may edit the selected profile's directory, project-discovery/trust, global skill disabling and preload fields in `config.yaml`. Rust performs revision-checked, locked atomic writes; the helper only prepares YAML and preserves unrelated fields. This does not authorize skill-content lifecycle writes, Hub lock changes, bundled synchronization or automatic project trust. Original skills CLI installation, update and removal behavior remains unchanged.

Explicit extension accepted 2026-10-18: [Pi invocation and update safety](../specs/0006-pi-skill-management.md) keeps CLI-managed visibility outside skill files and edits invocation metadata only for native Pi resources. Qualified package updates delegate to the user's original Pi 1.3.0 package manager, never a fork or a bundled replacement. The adapter owns source/local-content checks, reviewed affected scopes, installation baselines and field-only configuration recovery. Source files with unknown or modified content are not automatically overwritten; original CLI lock ownership is unchanged.

Explicit extension accepted 2026-10-18: the user-authorized Diff file restore discards a reviewed local file change in favor of its verified installed-source contents, or removes that selected local addition. It does not install, upgrade or uninstall a skill/package and does not write original lifecycle locks. Per-file confirmation and current-content/source checks remain required.

Explicit extension accepted 2026-10-20: local skill distribution may copy an installed directory or standalone skill document, or create a direct directory/file symlink through the existing Sync flow. Rust owns the small application-side relationship journal, destination checks, local-edit protection, recoverable directory replacement, propagation after successful source updates, and reviewed removal of owned copies/links (including broken links). Inventory/check operations remain read-only with respect to distributed content. Existing CLI and Agent locks are never written by this extension. Original lifecycle updates with associated targets use the unmodified CLI's explicit original-target add operation to avoid rewriting local distribution targets; successful source changes then propagate independently. Eve destinations retain root/subagent selection and use the pinned original formatter for converted copies. Standalone documents become a target folder containing only SKILL.md (copied or linked). No remote resolution is used for local sync/update checks. See spec 0003.

Explicit lifecycle clarification accepted 2026-10-20: application-owned content records support comparison, automatic associated-copy protection and field-only invocation recovery; they are not an additional authorization gate for user-confirmed original CLI installation/update/uninstall or local synchronization. Ordinary version checks do not retrieve npm archives. Exact installed-package reference retrieval is limited to configuration/default restoration, with no dependency-tree download or whole-package backup. Original locks remain owned by their original CLI.

## Consequences

- Upstream commands must be inventoried, including parameters, interaction requirements, structured output, side effects, and future GUI mappings. The first release need not expose every command.
- The desktop adapter must accommodate upstream's actual interfaces; a private versioned JSON protocol is no longer a prerequisite supplied by our CLI.
- The application bundles a fixed, unmodified upstream release and upgrades it with the application, leaving user-installed CLI copies untouched. The current CLI baseline is skills@1.7.4 (upgraded from 1.7.2 after contract audit). The 2026-10-28 runtime decision below supersedes bundling Node.
- Necessary read-only desktop extensions are allowed. The explicitly accepted [Pi skill configuration extension](../specs/0006-pi-skill-management.md) also writes Pi-native skill paths and filters; the original increment did not install, update or uninstall skill content. The explicitly accepted 2026-10-18 increment delegates Pi package updates to original Pi and restores invocation metadata without writing upstream locks or replacing either CLI lifecycle. Core state must not depend on human-oriented terminal output parsing; unsupported interfaces may lead to limited or deferred functionality.
- The first refactor supports global and project scopes. The current target validates local global/project requests and rejects non-local execution. SSH transport, remote identity, credentials and remote workflows are deferred and have not been implemented or verified.
- Explicit extension accepted 2026-10-16: independent Pi-native local skills may be moved to the OS Trash after path/content review. Shared, CLI-managed and package resources are excluded; no upstream locks, package lifecycle or permanent-delete fallback is introduced. See spec 0006.
- Implementation takes place on a new branch without legacy central-library compatibility or migration. Tests use isolated HOME, temporary projects, and test Agent directories; this decision does not authorize automatic deletion of existing user data.
- [The document index](../README.md) distinguishes project rules, glossary, active requirements and implementation evidence. Older managed-CLI ADRs/specs and source modules are historical; they do not define a compatibility requirement or an active app runtime.

## Codex skills and local plugins exception (2026-10-21)

The user approved stages A–C of [spec 0010](../specs/0010-codex-skill-plugin-management.md). Standard Codex skill installations remain under the bundled, unmodified skills CLI. The user's original Codex CLI provides native inventory and version-checked user configuration through a separately owned stdio App Server; local-marketplace plugin install/remove uses `codex plugin` JSON commands. Plugin resources are never sent to the generic skill uninstall backend. Package lifecycle writes remain owned by the original runtime, and the adapter never synthesizes installation records. The bounded desktop runtime-configuration restoration exception is recorded below. Writes are qualified against Codex 0.162.1; other versions retain standard lifecycle support and read-only observations when their protocol is usable. No model, authentication, session or application-version management is added.


## App-managed plugin update configuration (2026-10-24)

For the user-authorized update fix, reserved App marketplaces use the original CLI binary's explicit `plugin/install` App Server method against the actual, validated canonical marketplace manifest. The runtime rejects a temporary same-name catalog outside its canonical CODEX_HOME location. Other local/Git sources retain their frozen-source CLI path; source and installed-content guards and post-install verification remain in place.

Only `unified-computer-use`/`cua_repl` and `codex-app-tools`/`codex_app` from the canonical App-provided market receive a bounded configuration exception: after original installation, restore the known fields the desktop itself injects into `.mcp.json`, rebasing package-local command/argument/cwd paths to the new installation. This restores existing runtime configuration rather than installing package files; new script/tool/approval/timeout definitions remain the installer's reviewed source. The prior values are held only in operation memory, never added to logs or recovery records. Recovery stores only a comparison fingerprint for these packages and accepts old records without it. This does not authorize arbitrary cache edits, credential access, new runtime configuration or another lifecycle backend.


## Codex project plugin settings exception (2026-10-25)

The user explicitly authorized project-specific plugin enabled overrides while retaining original CLI ownership of installation, removal and updates. The original 0.162.1 config/value/write interface advertises filePath but rejects project files with configLayerReadonly (only user-config writes are allowed). Project configuration itself is supported and read by the original runtime. Do not redirect a project action to the user configuration.

Rust therefore performs one bounded native edit: the selected plugin's enabled field in the selected project's .codex/config.toml, or removal of that field to restore inheritance. It validates the original runtime's project layer/trust and higher-priority controls, rejects user-config/outside-project path resolution and read-only files, preserves unrelated TOML through the existing locked toml_edit version, and uses checked atomic replacement. A missing .codex directory is created only after confirmation; if original trust validation fails, the newly created empty directory is removed. Trust records are never created or changed. Original CLI readback verifies effective state. Account plugins keep the independent account service lifecycle; project writes never apply to them. This exception adds no plugin-content lifecycle backend and reads no original login credentials.

## Pi extension packages (2026-10-25)

The user authorized complete Pi package management under spec 0006. The qualified, unmodified managed Pi 1.3.0/1.4.0 package manager owns package install/remove/update and source identity. Its original resource selector prepares global/project loading choices in memory. Rust applies only the changed package/resource settings fields using the existing lock, revision and atomic-write mechanisms, preserving unrelated settings. Read-only resolution skips missing sources and does not load extension entry points. Built-in resources receive loading controls, not independent package lifecycle operations. This extends the earlier package-update-only exception; original skills CLI lifecycle and credential boundaries remain unchanged.


## System Node with an official fallback (2026-10-28)

The user authorized removing the bundled Node binary while retaining the pinned, unmodified skills CLI and all existing capabilities. Rust resolves a compatible system executable (Node >=22.20.0), including common desktop-visible installation locations, or an explicitly selected executable. Global settings expose the actual version/path, redetection, file selection and restoration of automatic detection. Runtime selection is app-wide and stored separately from Agent/project configuration.

Only when the selected/system runtime is missing or incompatible does the adapter download official Node 22.20.0 from nodejs.org. A shipped SHA-256 pin verifies the archive before extraction; Node, its license and the original bundled npm/npx are retained in application data (headers and documentation are excluded). Download failures leave user installations unchanged and permit explicit retry. A removed/replaced executable invalidates the in-process observation; unchanged calls reuse it without spawning another version check. No shell startup files or existing credentials are read. The original CLI bytes, locks and lifecycle ownership are unchanged.

Development/build commands still require Node; staging verifies the original helpers using the build process executable and no longer downloads or stages a Node sidecar. Runtime and packaged-app acceptance evidence is recorded in plan 0005.
