# UI design baseline

Status: Active project guidance. Established 2026-10-15; the Codex-inspired inventory/detail/dialog sample was approved for product-wide promotion on 2026-10-23. This is the UI design authority; research reports retain dated evidence. Establishing this baseline does not mean existing pages already comply or authorize a redesign outside the requested task.

## Before UI implementation

1. Read this baseline, `components.json`, the relevant local component implementations and the nearest conforming surface. Inspect the current page and its changed states; select reusable components before editing.
2. Apply the task-specific UI skills in [skill usage](../agents/skill-usage.md). Establish or refresh project context with `pnpm exec shadcn info --json`; use the documented package runner for component documentation and fetch the returned URLs. Match API examples to the installed Radix base and local exports. Reuse verified lookups while configuration and interfaces are unchanged. A CLI-inferred preset, especially fallback values, is not the application's active palette.
3. Map each addition to a field, action, state or help location in the existing layout. Identify a missing shared primitive explicitly; add it once through the project's shadcn workflow and adapt it to existing tokens instead of styling a raw control independently in a page. Preserve unrelated local component customizations.
4. State the reference surface and any actual design gap in the work update. Resolve routine composition within this baseline; get a design decision when changing navigation, card structure or shared visual behavior beyond the authorized scope.

Completion: the implementation has an identified reference, applicable component interfaces and a placement for every new visible element. A failed lookup requires diagnosis and a permitted retry or official-source alternative; verify an offline fallback against installed source and report its limits if retrieval remains blocked. Do not declare an API checked merely because its documentation URL was found.

## Theme and component ownership

The application includes eight palettes from [tweakcn](https://github.com/jnsahaj/tweakcn), a theme editor for shadcn/ui, and the locally adapted Codex palette approved through the [design sample](codex-preview.md). shadcn supplies component structure/style; Radix supplies primitives; Tailwind supplies utilities. These are separate responsibilities.

| Layer | Authority in this repository | Meaning |
| --- | --- | --- |
| Component setup | [components.json](../../components.json) | `radix-nova`, Radix base, neutral base color, Lucide icons, `@/` aliases. This is not the selected runtime color theme. |
| Palette data | [theme-presets.json](../../src/lib/theme-presets.json) | Locally bundled tweakcn presets, the separately attributed Dark Forge community export, and the approved local Codex palette. [Theme sources](../research/ui-theme-sources.md) owns attribution and import evidence. No runtime theme download. |
| Theme application | [appearance.ts](../../src/lib/appearance.ts) | Applies light/dark tokens; `colorTheme` selects the palette (new/missing configuration default Codex; explicitly saved palettes remain unchanged), `theme` selects system/light/dark independently. Typeface and base size are separate preferences. |
| Token mapping and layout | [index.css](../../src/index.css) | Semantic colors, app font, project radius mapping, focus treatment, inventory container queries and reduced-motion behavior. |
| Shared controls | [ui/](../../src/components/ui) | Locally maintained shadcn components with project-specific variants, including inventory Card surfaces and compact display-mode Toggles. Read these files before assuming upstream defaults. |
| Persistence and native chrome | [preferences.rs](../../src-tauri/src/preferences.rs), [window-appearance.ts](../../src/lib/window-appearance.ts) | Native preferences persist appearance; startup cache stores appearance only. Native window background follows the sidebar token. |

Use `background`, `card`, `popover`, `sidebar`, `primary`, `muted`, `border`, `input` and `ring` by their semantic roles. Apply a foreground/background token pair together. Use existing component variants for radius, spacing, type and focus; page classes compose layout rather than inventing per-page skins. Add any needed shared variant centrally and check affected consumers. Palette changes must not rewrite navigation or information hierarchy.

Typography inherits the user's font and 14/16/18 base-size preference (16 default). System is the new/missing configuration default; bundled Geist, serif and monospace remain selectable, and explicitly saved fonts remain unchanged. Regular UI text is approximately 14px, inventory descriptions 13px and metadata 12px at the default root size. Page titles use 28px and dialog titles 20px; Markdown retains its own reading hierarchy. Typography scales with the existing size preference. Shared radius and elevation values belong to index.css and component variants; imported palette geometry/shadows are not applied at runtime. Theme samples may render their own swatches; ordinary content uses semantic tokens.

Existing explicit exceptions: Agent status colors use the shared installed/configuration/absent tokens; `Switch` uses the centralized focus/accent `ring` token for its checked state with a white thumb; `AgentLogo` preserves Agent brand assets. The update glyph uses the centralized light/dark `skill-update` semantic token. These are not permission to hardcode other status colors or recolor brand icons. Ordinary store/space/project icons follow their theme/currentColor treatment. Preserve the subtle native page scrollbar and shared focus treatment.

### Read-only update checks

Managed skills, Pi plugins and Codex plugins share the same non-blocking update-check behavior in global and project views. A check is a read, not an installation or settings mutation: only its Check updates action shows the existing spinner, retains its label/width, exposes aria-busy and prevents duplicate checks. Keep sidebar/scope/Agent navigation, search, filters, details, directory links and unrelated actions available. Single-plugin checks follow the same rule as toolbar checks; they do not enter application-wide busy state or disable the page. Actual installs, updates, removals and enable/disable writes retain their existing mutation restrictions and confirmations.

Preserve the current inventory, counts and filter selections during a check. Updating one plugin invalidates only that plugin's update result (including installations of the same source actually affected by the update); other plugins retain their confirmed available-update icons during the operation and after success or failure. A full explicit recheck or context change may still replace its own check results. Display confirmed update actions through the existing available-update affordance; checking alone opens no toolbar confirmation. Refresh, context changes and relevant writes invalidate older check responses: late success, errors, reviews and cleanup must not overwrite a newer context, write result or check. A failed read keeps the current inventory and uses the existing concise retry feedback, without adding a blocking page, banner or card notice.

## Enforced shadcn composition rules

The [component catalog](component-catalog.md) is the selection inventory, not a requirement to install all components. Check it and the installed exports before choosing a primitive. Existing business wrappers must not erase the distinction between a confirmation, an editing task and a long execution flow.

| Decision | Required composition |
| --- | --- |
| A short destructive decision | AlertDialog: Title, concise Description, object identity when necessary, Cancel and destructive Action. Use the standard 520px width for a single decision and the wide 600px variant for batch/source reviews, bounded by viewport gutters. Compact means concise content and spacing, not a narrow dialog. No fixed height, header/footer dividers, tinted footer, redundant close icon or nested object Card. Default focus goes to Cancel. |
| Editing or collecting input | Dialog through the existing Modal; FieldGroup/Field for inputs. Keep the established draft, busy and focus-return behavior. |
| Long selection, review or execution | Existing flow Modal and review components, with one owning body scroll region. Display scope/affected targets only when they change the decision. Do not flatten meaningful destructive consequences to obtain a small dialog. |
| Peer page navigation / short value selection | Tabs with TabsList/TabsTrigger for pages; ToggleGroup for a short option set; Select for longer option lists. Never recreate selected state with independently styled Buttons. |
| Secondary actions / contextual information | DropdownMenu for actions, Tooltip for short noninteractive text, Popover for interactive or longer contextual content. Never put actions inside a Tooltip. |
| Status, feedback and loading | Existing Badge/AgentStatusBadge, Alert for durable contextual feedback, Sonner for transient results, Empty and Skeleton for their respective states. Avoid styled substitutes. |

Component rules apply to every new or changed surface:

- Keep SelectItem in SelectGroup, menu items in their menu group, TabsTrigger in TabsList, and Card content in the appropriate Header/Content/Footer regions. Dialog and confirmation surfaces require an accessible Title and a meaningful Description when consequences need explanation.
- Use the installed Radix `asChild` interfaces and current local exports. Button has no invented loading prop; compose disabled/busy state and an existing spinner icon. Preserve focus return, keyboard behavior and disabled semantics. Async confirmation must remain open while pending; close only after the existing handler succeeds, retaining retry/error handling.
- Page `className` composes layout. Component colors, typography, radius, state styles and density belong in shared variants/tokens, not repeated per-page overrides. Prefer existing variants; use `cn()` for conditional classes, gap-based spacing and `size-*` for square dimensions. Overlay stacking belongs to the shared primitive, never the consumer.
- Use the existing icon-button sizing and accessible names; inline Button icons use `data-icon` when applicable. Preserve brand assets. Do not add icons or media to a confirmation merely to decorate it.
- Read the official example before implementation, then adapt its composition to the product semantics. Permanent-delete sample wording does not describe recoverable Trash operations. Required impact must be accurate about reload/session behavior; avoid unsupported claims about immediate unload or recovery guarantees.
- When registry generation proposes overwriting a customized dependency, inspect dry-run/diff/view first and retain the local file. Inspect generated imports/dependencies; reuse the local `cn` utility and existing wrappers rather than accepting redundant packages. Update the catalog only for files actually present. A new primitive does not authorize a preset change or a bulk page rewrite.

Result surfaces show completion counts/names and only actionable exceptions. Successful removal must not expose obsolete path links or a View skills action; successful install/update may offer View skills only when the returned inventory confirms a completed skill. Retain paths for unresolved filesystem/content issues, not as a duplicate success receipt. Logs remain optional collapsed diagnostics; omit empty logs and never manufacture success logs by serializing every verification record. Creation/test paths can remain when the next action uses those files. Review each dialog's source/selection/review/pending/success/partial/failure/empty states rather than applying one content template to all phases.

Update confirmation includes selected skills with a confirmed available source change, including locally modified skills; the existing overwrite consequence covers explicit replacement. Local modification and unavailable auxiliary history never disable the update action; compare complete revisions, never abbreviated labels. Omit the redundant scope row. Show the actual update count in the existing title and confirmation action. Use one compact aligned list: skill name, old revision, arrow and new revision share columns, with standard row spacing and no repeated version labels, nested cards or extra actions. Use the same 7-character hash formatting as details, preserving semantic versions; long names wrap within their column without shifting version columns.

Project import and reinstall reuse the task Modal. Give each one a concise functional Description; keep project context and aligned skill/source rows in the body. Import discovers skills before Agent/mode selection, then reviews and installs. Reinstall displays local installation records before remote inspection and explicitly describes current-source installation rather than historical rollback. Keep advanced rules folded with label-side help, examples and actual cleanup consequences. Read-only checks stay local to the flow and use the shared bottom-right progress notification; cancellation must ignore late results. When the project flow changes stages, reset its body scroll to the top without remounting the form; rechecks within the same stage retain the reading position.

Current confirmation coverage: Pi local removal, managed single/bulk/same-source removal, standalone skill/package update and unsaved Pi settings use AlertDialog. Installation/sync/dependency/restore workflows, project editing and result inspection use their task Modals. Do not treat a confirmation step inside a wizard as a separate standalone dialog.

Modal and confirmation content must stay within viewport gutters and 90dvh. Keep header and actions outside the owning body scroll region; content-bearing confirmations reuse AlertDialogBody. Shared form groups/fieldsets allow shrinking with min-width zero. Long selected Agent summaries remain one truncated line beside the protected count; the picker retains a usable list height while any excess surrounding form content scrolls in the Modal body. Large Agent/skill selections, expanded details, long names/paths and larger text must not widen the dialog or move actions outside the viewport.

These rules supplement the existing theme, inventory, settings and toolbar rules; they do not authorize a whole-app redesign. Deviations found outside the requested scope must be recorded as findings rather than silently repaired.

## Information hierarchy and copy

Version metadata uses the existing animated loading glyph with “加载中…” / “Loading…” while its read is pending. Show “未知” / “Unknown” only after a successful read confirms no version; read failures use failure feedback. Do not use installation/update busy state as a substitute for version-read state or replace an already resolved version with a loader for unrelated work.


Prefer whitespace and alignment to decorative dividers (explicit user preference, 2026-10-28). Settings rows and read-only preview lists have no per-row separators by default. Retain actual control boundaries and necessary structural edges; do not turn every item or group boundary into a horizontal line. Apply this to affected surfaces without redesigning unrelated pages.

Keep Skills Space compact: show what identifies the object, what the user can do and what changes their decision. Every visible sentence must serve one of those purposes. Delete redundant or unnecessary copy rather than moving it into help. Help is optional: add it only for a real secondary question that the field, example or action does not already answer; familiar actions such as Save do not need an adjacent help trigger. Translate implementation requirements into behavior rather than publishing them as explanatory copy.

All product copy must be concise, clear and unambiguous, including labels, help, notifications, confirmations and errors in both languages. In Chinese, use 配置 for a configuration section, 配置方案 for a named Profile, and 配置文件 only for an actual file; do not use 配置档. Preserve technical identifiers and stored Profile names. Use familiar user terms and precise objects, states and actions; omit internal jargon, vague qualifiers and redundant explanation. Error copy must make the failed action and actual outcome clear from the message and its immediate context; state a cause only when known, and give a next step only when an existing action can perform it. Do not use bare instructions such as "review", "verify" or "retry" without identifying what to review or which available action to take. Never shorten copy by removing necessary meaning or lengthen it to justify an unnecessary notice.

Feedback must identify the affected object and actual outcome, and appear only when it changes a user decision or an existing action can resolve it. Do not expose internal inspection, baseline, fingerprint or recovery states as routine card/detail notices. Package-wide state must not be attributed to an individual skill; missing evidence is not a confirmed content edit. Diff operation failures reuse the existing bottom-right error notification instead of adding an error box or explanation row to the content or restore dialog. Do not relocate meaningless feedback into a tooltip, toast or modal, or invent buttons, explanatory panels or repair workflows to justify it. Reuse existing actions and shared feedback components; actionable errors must name the affected target and lead to a working existing retry or correction path. Keep raw diagnostics in existing collapsed logs. Do not invent a cause for an unknown error or truncate away its affected object; use an action-specific failure summary with its existing retry path and retain available diagnostics. Success, no-change and failure states are mutually exclusive; no-update checks use transient feedback, not a standalone confirmation. Preserve explicitly requested capabilities when cleaning feedback. Build/type checks do not establish semantic or visual acceptance; report actual observations and remaining checks separately.

| Information | Placement |
| --- | --- |
| Identity, current value, primary action | Main surface, concise label or icon plus short text |
| Familiar repeated action (back, refresh, open directory, uninstall) | Existing icon-button variant with accessible name and a short tooltip; retain text when context would otherwise be ambiguous |
| Field format or typical input | A short placeholder/example with a persistent accessible label; keep necessary constraints available after typing |
| Rule syntax or secondary explanation | A focusable `?` help trigger beside the label; short noninteractive explanation in Tooltip, longer/copyable/interactive content in a click-open Popover |
| Local conflict or unsupported action | Stable status/action slot plus a concise explanation on focus/hover or in details; keep essential blocking consequences visible in the relevant confirmation |
| Save result | Local feedback after the action; keep feedback concise; Pi uses the single page-level reload notice defined below instead of repeating it after each action |
| Raw paths, provenance, technical diagnostics | Details, expandable diagnostics or the relevant field; display HOME as `~` |
| Architecture, ownership implementation, request placement constraints, future scope | Development documentation; not default page copy |

Do not use help to hide failures, destructive effects or a required user decision. A tooltip is not a container for buttons, links or a miniature manual. Help must work with keyboard focus; icon actions need an accessible name independent of hover. Success needs no paragraph explaining the verification engine. Check Chinese and English for equivalent, concise meaning.

## Surface contracts

- **Desktop shell:** use a 16rem sidebar with compact branding and an unbordered transition to the full-height content plane. Use a small theme-derived corner radius and a narrow outer gutter, without a prominent enclosing border or shadow. Use the installed shadcn SidebarHeader/Content/Footer structure: top-level navigation and scope groups are separate, group headings/actions use SidebarGroupLabel/Action/Content, project rows use SidebarMenuButton with an independently anchored SidebarMenuAction. On macOS, keep native window buttons and the collapse trigger in a dedicated 44px draggable title row, above and independent of the brand row. Place the trigger near the expanded sidebar right edge and beyond native window buttons when collapsed; never imitate native window controls. On other platforms retain the content-inset trigger. Use PanelLeftClose/PanelLeftOpen for expanded/collapsed state; retain the 28px brand Logo and full-width brand name without sharing space with the trigger. Icon collapse must retain distinguishable Global/Projects scope headings (Globe/Folders icons with localized full accessible names and shared Tooltips) and existing project/Agent entry icons; do not inherit the registry’s hidden-group-label treatment for these scope selectors. Keep the trigger reachable and collapse footer controls into an icon column; expanded controls retain their labels. Preserve hover-only category affordances, single-click project folding, sorting and equal Agent indentation across scopes. Omit sidebar and footer separator lines; the main scrollbar track is transparent and borderless. Fix the document/shell to the viewport; scroll the main content and sidebar content independently. Clip the main scroll surface to its rounded pane without document overscroll. Main page headings, navigation and collection actions form separate spatial levels; preserve semantic theme tokens and all sidebar navigation behavior.

- **Inventory collections:** global/project Skill Space and Agent pages share compact quiet Tabs for managed and Agent-native resources. Use the same quiet Tab treatment in the store and settings; include compact collection icons and no divider below the navigation row. Collection counts belong in the Tabs and report totals for the current scope or Agent management page, independent of search and list filters; do not repeat an inventory total above the cards. Put the selected collection toolbar below the collection Tabs using the standard toolbar layout below. Preserve one card structure; gate actions by actual capabilities rather than appending ownership explanations or unavailable controls. Native origin labels distinguish bundled, package and local-folder skills. Agent enhancements are scoped to the current Agent management page, including details and batch operations. Skill Space Agent filters narrow the list only; changing a filter must not switch action menus, card controls or the detail action context. Configuration-only actions may apply to both managed and native skills when the Agent supports them; managed skill files remain unchanged by these enhancements. Native content edits and Trash actions require native ownership and the existing shared-file protections. Evaluate batch eligibility per action rather than granting every action from one selection rule. Skill Space exposes no Agent-specific controls or runtime status, regardless of its Agent filter. Preserve truthful source/path metadata and read-only ownership inspection used to protect the original CLI lifecycle.
- **Skill cards:** follow [Skill card layout](#skill-card-layout) for fixed information placement, hint aggregation, icon treatment and density. Preserve one layout across managed/native and global/project/Agent collections. Pi independent local removal uses the shared AlertDialog with identity/path and the Trash consequence; shared/package cards do not expose it. Native Pi source filters reuse the Codex Plugin skills submenu composition: keep All sources and Local directories as first-level choices and put package display names under 插件技能 / Plugin skills, retaining complete canonical source identities as filter values. Pi package source filters display 本地目录 / NPM包 / Git 仓库; card metadata abbreviates NPM包 to NPM and uses the npm mark. Scoped package names omit the scope in display titles while retaining the full identity for operations and About metadata. Pi package detail/manage views follow the Codex split: one introduction in the body of both views before detail-only examples, lifecycle actions in management, clickable native skill rows, and non-skill resource counts in About. Skill count belongs to the skill section heading; management uses the shared skill Switch beside the detail action, while the card retains whole-package enablement. Pi cards without declared artwork omit a generic title icon; source icons remain in footer metadata. Package title-right Switches change all package resource types together; project choices remain project overrides. Pi package batch controls reuse the existing collection selection bar and confirmation flow. Eligible Pi managed and native cards expose invocation via one bottom icon toggle (Sparkles for automatic selection, Hand for manual invocation), labeled “自动选择” or “手动调用”. Managed invocation uses external preferences: explicit automatic/manual selection overrides the source field, and an absent preference follows the source default. Native invocation edits only its field. Shared and CLI-managed source files remain unchanged; other package metadata stays read-only. Clicking always switches directly from the displayed invocation state, with only its short state Tooltip; extension deployment belongs to saving and is not a separate card repair action; the top-right Switch remains enable/disable. Batch enable/disable and invocation each submit once and update the collection once; writing separate native skill files does not require separate UI requests. Native Pi bulk selection uses file identity, and each action remains gated by its actual capability. In bulk-selection mode the whole eligible card is a single checkbox: clicking its title, description, metadata or blank area toggles selection; normal detail/navigation/enable/remove controls are inert until selection mode ends. Expose the card checked/disabled state, allow Space/Enter selection with a visible focus indicator, and prevent the decorative inner checkbox from causing duplicate toggles. Keep existing eligibility/busy restrictions.
- **Inventory empty states:** Skill Space and global/project Agent collections reuse `InventoryEmpty` with the installed Empty composition, a relevant icon and no enclosing dashed frame. Distinguish unavailable inventory (Retry), uninstalled Agent (Detect again), active search/filter with no matches (Clear filters), empty native collection and first-use managed collection (Add skill). Clear filters resets search, optional Agent, Pi status/package and Hermes status/origin filters together; the selected Agent/scope is navigation, not a filter to clear. Native empty states need no artificial action. Render descriptions only when they add useful context; never present a read failure as no skills.
- **Agent management rows:** use a compact two-column grid (one column in narrow containers) with aligned drag handle, brand, identity, installed count, status, reserved settings slot and visibility switch. Preserve card dragging and four-direction keyboard ordering across the grid. Configurable and static Agents share the same identity metrics; Pi, Hermes and DeepSeek Harness have the settings action; DSH settings follow the approved static skill-field subset in [spec 0009](../specs/0009-dsh-native-skill-management.md); complex inheritance and dynamic configuration remain read-only. Group settings rows into Enhanced integration / General support (增强适配 / 通用支持), derived from declared native capabilities. Preserve one search/status toolbar and the existing full saved order; drag and keyboard moves stay within each group without moving other-group slots. Hermes settings reuse the Pi title-row Back button and Field/Card compositions; profile settings stay distinct from the selected project inspection context. Card switches edit profile disabling; Loading controls represent on-demand loading or session preload, not manual-only invocation. Use Clock for deferred/on-demand loading and Zap for session-start preload, with the current mode in the shared Tooltip. Use the same ghost icon-sm button in both loading modes, with the standard 16px glyph and transparent resting background. Preload state changes the glyph, not the button background; do not use a checkmark to imply preload timing or add another card text row. Disabling a skill must not disable editing its preload preference or implicitly clear that preference; changing preload must not enable it. Disabled skills do not match either active loading filter. Hermes managed and native collections reuse the existing batch selection bar and the same enable/disable controls as Pi; enable/disable and preload changes submit once per batch. Card loading hints report the current mode (on demand/session preload), without mixing in the reverse action label.
